# AI 算法与限制

[返回 README](../README.md)

AI 使用有限预算的 Expectimax 和手工启发式评分，目标是在响应时间与决策质量之间取得实用平衡。它不是全局最优求解器；“深入”增加允许的搜索工作，并不保证每一步都优于其他档位。

## 规则与搜索

每个有效移动后，游戏从空格中均匀选择出生位置，再以 90% / 10% 的概率生成 2 / 4。游戏和 AI 使用同一个 `SPAWN_DISTRIBUTION`。

搜索交替执行两类节点：

- **Max**：模拟合法方向，选择价值最大的方向。
- **Chance**：枚举或采样出生位置，并计算 2 / 4 的加权期望。

`choose_move` 先计算全部合法方向的一步评分作为后备，然后迭代加深。只有所有合法方向都完成的深度才会替换已有结果，避免将某个方向的未完成搜索与其他方向比较。

返回的 `SearchResult` 包括方向、价值、已完成深度、节点数、耗时和各方向价值。深度 0 表示使用后备评分。平局按 `DIRECTIONS = (U, R, D, L)` 的固定顺序决定，因此不需要消耗游戏随机源。

## 搜索档位

`SearchSettings` 和 `AI_PROFILES` 定义集中在 [search_profiles.py](../search_profiles.py)，也可从 `ai.py` 导入。

| 设置 | 快速 | 均衡（默认） | 深入 |
| --- | ---: | ---: | ---: |
| 默认时间预算 | 28 ms | 85 ms | 220 ms |
| 最大深度 | 3 | 5 | 6 |
| 3～4 阶：深度 / 位置目标 | 3 / 16 | 5 / 16 | 6 / 16 |
| 5 阶：深度 / 位置目标 | 2 / 12 | 3 / 16 | 4 / 24 |
| 6～9 阶：深度 / 位置目标 | 1 / 8 | 2 / 16 | 3 / 24 |
| 10～40 阶：深度 / 位置目标 | 1 / 8 | 1 / 16 | 2 / 32 |

表中深度是上限，位置数是采样目标；实际完成深度取决于局面与预算。3～4 阶最多 16 个格子，因此枚举全部空位。大棋盘的各档会允许不同数量的出生位置，深入档还允许更高深度。

空位超过目标时，将坐标按正方形的旋转与镜像轨道分组，分层选取整组中的空位。这样旋转或镜像局面不会因为固定坐标采样而偏向某个方向。每组至多 8 个位置，稀疏组可能使实际位置数低于目标；自定义目标小于 8 时，至少选择一组，也可能超过该目标。

每个被选位置的概率重新归一化，再保留 2 / 4 的 90% / 10% 比例。这是对真实出生分布的近似：没有被选中的位置不参与该次期望，保留对称性也不能保证估计无偏或最优。

## 预算与复现

```python
from ai import ExpectimaxAI

board = ((2, 0, 0, 0), (2, 4, 0, 0), (8, 4, 0, 0), (16, 8, 2, 0))
engine = ExpectimaxAI("balanced")
result = engine.choose_move(board, node_budget=2400)
print(result.direction, result.depth, result.nodes)
```

- 不传预算：使用档位默认时间预算。
- 只传 `node_budget`：关闭默认时间限制，便于在相同代码、依赖和缓存条件下复现。
- 只传 `time_budget_ms`：使用显式时间约束。
- 两者都传：同时约束，任何一个耗尽即回退至已完成结果。
- 预算为 0：返回后备评分，不展开 Expectimax；负数、布尔值和非整数预算会被拒绝。

节点统计包括实际访问的概率叶子。本次搜索的 Max / Chance 缓存命中不消耗节点；即使命中全局评分缓存，访问叶子仍计节点。时间检查发生在节点和关键分支边界；输入校验、后备评分及一个不可抢占的计算调用仍可能使总耗时超出预算。它是工作预算，不是硬实时保证。

不要并发调用同一个 `ExpectimaxAI` 实例。应用通过一个 `AIWorker` 串行处理搜索；独立并发任务应各自创建实例。

## 评分与数值表示

叶点评分结合空位、相邻平滑度、单调性、相邻合并潜力、最大方块靠边或靠角，以及八种旋转镜像蛇形路径的层级。合并得分还带有对数形式的即时奖励。

这些因素和权重是启发式设计；角落偏好不是强制规则，启发式价值也不是最终得分或胜率。调整权重、采样或浮点累加顺序后，应通过完整对局评估策略质量。

NumPy 数组保存方块指数：空格为 0，方块 `2**k` 为 `k`。大棋盘对浮点可表示的二次幂使用向量化 `log2`；超过浮点范围的 Python 大整数回退到 `bit_length` 编码，避免真实方块溢出。

最末层 Chance 复用一份父棋盘指数数组，逐个设置出生格、评分并恢复该格，避免为每个出生结果构造完整棋盘并重新编码。其他搜索层继续使用不可变棋盘，保证模拟隔离。

Numba 内核使用固定签名、`cache=True`、`nogil=True`、`fastmath=False`，共享不同棋盘尺寸的编译版本。首次导入可能编译，稳态基准应排除这段时间。后台线程中的纯 Python 搜索仍可能竞争 GIL，不能把编译内核释放 GIL 解释为整个 AI 与 UI 完全互不影响。

## 缓存

- 4 阶及以下的估值和模拟移动使用有界全局缓存，跨步复用。
- `_merge_short_line` 缓存长度不超过 8 的行，因此也适用于 5～8 阶；更长行不进入该缓存。
- 每次搜索分别维护 Max、Chance、出生结果和采样位置缓存。
- 正常游玩保留缓存；性能比较使用 `clear_search_caches()` 清空计算缓存，统一起点。

缓存容量是时间与内存的取舍。修改容量前，先观察实际命中率和长期运行内存；减少容量并不一定改善整体体验。

## 如何判断改进

计算耗时与对局质量应分别评估，明确局面、样本量、预算、机器和缓存条件。使用固定节点预算比较相同局面的开销，再以多个完整对局比较分数、最大方块和 2048 达成率；少量短流程不能证明胜率提高。提交结果时注明验证方法，见 [贡献指南](../CONTRIBUTING.md#验证改动)。
